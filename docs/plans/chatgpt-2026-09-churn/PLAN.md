## Resolution model (binding, R1) — how pack v2 scoping works

Verified against `driftwatch/src/core.js` (2026-09-21): `inside:X` resolves X with `querySelectorAll` in the SAME scope (descendants only, scope root excluded — core.js:83, filter at :54-71) and caches exactly ONE `r.el` (:63) for containment (:67); `resolve()` itself returns ALL matches in `els` (:145-146). Therefore, NO engine change is needed and none is made:

1. **Exchange enumeration**: `resolve('exchangeRoot', document).els` = every exchange, in DOM order. This is the ONLY document-wide resolution consumers perform for per-exchange concepts.
2. **Per-exchange anchors** (`userUnit`, `assistantUnit`, `assistantMarkdownRoot`, `responseActionBar`, `codeBlock`, `copyResponseButton`, `editMessageButton`) are resolved as `resolve(anchor, exchangeEl)` — the exchange element IS the scope. Their strategies are written for that scope (no root-prefix selectors, no exchange-scoping `requires`).
3. **Pack v2 rule**: no strategy uses `inside:exchangeRoot`. Under an exchange scope, `inside:` may only reference anchors that are strict descendants of the exchange (e.g. `copyResponseButton` → `inside:responseActionBar`; `assistantMarkdownRoot` → `inside:assistantUnit`; `codeBlock` → `inside:assistantMarkdownRoot`). Document-scoped `inside:` is reserved for singletons: `composer`/`sendButton`/`stopButton` → `inside:composerForm`.
4. **Consumers must never enumerate per-exchange anchors document-wide** — document-scoped `inside:` containment checks only ONE resolved `.el`, silently excluding every other exchange (review finding 2).
5. `audit()` (document-scoped) remains a health signal; per-anchor statuses it reports are judged against the expected-status table (R4), never "all ok".
6. The engine change "`inside:` should accept a matching scope root" is NOT needed by this plan and is recorded in [driftwatch/docs/ROADMAP.md](file:///C:/Windows_software/driftwatch/docs/ROADMAP.md) Deferred with that reason.
